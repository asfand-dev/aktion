# Aktion for JetBrains IDEs — contributor guide

This is the **internal / maintainer** documentation: how the plugin is
architected, how to build, run, and debug it from a checkout, and how to publish
it to JetBrains Marketplace. For the **public, user-facing** overview, see
[`../README.md`](../README.md).

---

## Architecture

```
src/tooling/*  (the runtime's DOM-free analysis: parser, schema, formatter)
      │
      └── src/language-api.ts  ──►  editors/vscode        in-process (JS host)
                               ──►  editors/lsp           LSP over stdio
                               │         │
                               │         └──►  editors/jetbrains  (this plugin)
                               │         └──►  Neovim / Helix / Zed / Sublime / Emacs
                               └──►  docs/assets/playground.js    in-page (browser)
```

**This plugin contains no language logic at all** — no lexer, no parser, no
component list, no builtin list. It is an LSP client plus three small pieces of
glue. That is a deliberate constraint, not an accident: the repo's
[`editor-tooling-sync`](../../../.cursor/rules/editor-tooling-sync.mdc) rule
requires that anything which inspects Aktion source lives in
`aktion-runtime/language`, so the editors can never disagree with the runtime.

A Kotlin reimplementation would have meant a second parser, a second schema
validator, and a second copy of every component signature — three things
guaranteed to rot. Running the real thing over LSP costs one Node process.

### The four Kotlin classes

| Class | Job |
| --- | --- |
| [`AktionLanguageServerFactory`](../src/main/kotlin/dev/aktion/jetbrains/AktionLanguageServerFactory.kt) | Hands LSP4IJ a connection provider. Nothing else — every feature is negotiated from the server's `initialize` response, so new capabilities need no change here. |
| [`AktionLanguageServerProvider`](../src/main/kotlin/dev/aktion/jetbrains/AktionLanguageServerProvider.kt) | Builds the `node server.mjs --stdio` command line and reports a missing Node with an actionable notification. |
| [`AktionServerAssets`](../src/main/kotlin/dev/aktion/jetbrains/AktionServerAssets.kt) | Finds Node and `server.mjs`. |
| [`AktionSemanticTokensColorsProvider`](../src/main/kotlin/dev/aktion/jetbrains/AktionSemanticTokensColorsProvider.kt) | Maps the runtime's semantic-token legend onto platform `TextAttributesKey`s. The JetBrains counterpart of the VS Code extension's `semanticTokenScopes`. |

Plus [`AktionTextMateBundleProvider`](../src/main/kotlin/dev/aktion/jetbrains/AktionTextMateBundleProvider.kt)
(lexical colouring) and [`AktionSettings`](../src/main/kotlin/dev/aktion/jetbrains/AktionSettings.kt) /
[`AktionSettingsConfigurable`](../src/main/kotlin/dev/aktion/jetbrains/AktionSettingsConfigurable.kt)
(the settings panel).

### Three design decisions worth knowing

**1. LSP4IJ, not the platform's own LSP API.** The IntelliJ Platform has
`com.intellij.platform.lsp`, but it is **paid-tier only** (IDEA Ultimate,
WebStorm, PyCharm Professional, …) — it does not exist in IntelliJ IDEA
Community. It was also still being renamed as of 2026.2, when JetBrains
open-sourced it (`LspServer` → `LspClient`, provider →
`LspIntegrationProvider`). [LSP4IJ](https://github.com/redhat-developer/lsp4ij)
works in every IDE from 2024.2 up, Community included, with a stable API. That
reach is worth the extra dependency prompt at install time.

If you ever want to *also* support the native API, add a second, optional module
gated on `com.intellij.modules.ultimate` — do not replace LSP4IJ, or Community
users lose the plugin.

**2. No `FileType` for `*.aktion`, mapped by file-name pattern instead.**
Registering a `FileType` switches TextMate **off** for the matching files, which
would cost us the generated grammar. LSP4IJ documents `fileNamePatternMapping` as
the recommended approach for exactly this case, so `plugin.xml` uses:

```xml
<fileNamePatternMapping patterns="*.aktion" serverId="aktion" languageId="aktion"/>
```

The trade-off: no custom file icon in the Project view, and no PSI. Neither is
worth a hand-written Kotlin lexer.

**3. Two layers of colour.** TextMate paints the lexical layer (comments,
strings, numbers, keywords, `$`-builtins) the instant a file opens, before the
server is up. Semantic tokens from the server then refine it — that is what
distinguishes a library component from one you wrote. If TextMate is disabled you
keep the semantic layer; if the server is down you keep the lexical layer.

### Generated assets

Two directories are generated by [`scripts/sync-assets.mjs`](../scripts/sync-assets.mjs)
and are **gitignored** — never hand-edit or commit them:

| Path | Generated from |
| --- | --- |
| `server/server.mjs` | `editors/lsp/dist/server.mjs` (built on demand if missing) |
| `textmate/bundles/aktion/` | the runtime's `grammarSpec` + `builtinCatalog` |

The Gradle `syncAssets` task runs the script, and both `prepareSandbox` and
`buildPlugin` depend on it — so you cannot ship a build whose grammar or server
disagrees with the runtime.

Note that the TextMate grammar generated here is **not** the same file the VS Code
extension uses. VS Code's is a thin overlay that `include`s its built-in
`source.ts`; IntelliJ cannot be relied on to have `source.ts` registered, so this
one is self-contained and includes `source.ts` last as a bonus. The *vocabulary*
of both comes from the same runtime catalogs. The reasoning is written out at the
top of `sync-assets.mjs`.

## Prerequisites

- **JDK 21** (the Gradle toolchain requests it; the IntelliJ Platform 2024.2+
  needs 21).
- **Node.js 18+** — to build the language server and generate the grammar.
- **Gradle**. The wrapper JAR is not committed, so materialise it once:

  ```bash
  cd editors/jetbrains && gradle wrapper --gradle-version 8.14.3
  ```

  After that use `./gradlew`. (If you have no Gradle at all, open
  `editors/jetbrains` in IntelliJ IDEA and let the bundled Gradle import the
  project — it will generate the wrapper for you.)

## Building

```bash
# 1. Build the runtime so dist/language.js exists (repo root)
npm install && npm run build

# 2. Build the plugin
cd editors/jetbrains
./gradlew buildPlugin
```

The distributable lands in `build/distributions/aktion-jetbrains-<version>.zip`.

`buildPlugin` runs `syncAssets` first, which builds `editors/lsp` if needed and
regenerates the TextMate bundle. Step 1 is still worth doing: without a fresh
`dist/language.js`, `sync-assets.mjs` falls back to bundling the TypeScript
source on the fly, which works but is slower.

Useful tasks:

```bash
./gradlew syncAssets          # regenerate server/ + textmate/ only
./gradlew runIde              # launch a sandbox IDE with the plugin installed
./gradlew verifyPlugin        # IntelliJ Plugin Verifier against recommended IDEs
./gradlew signPlugin          # sign (needs the CERTIFICATE_CHAIN / PRIVATE_KEY env vars)
./gradlew publishPlugin       # upload to Marketplace (needs PUBLISH_TOKEN)
```

## Running / debugging it

```bash
cd editors/jetbrains && ./gradlew runIde
```

This launches a sandbox IDE with the plugin and LSP4IJ installed. Open a
`.aktion` file — for example `docs/demos/mini-apps/admin-dashboard.aktion` from this
repo, or a project scaffolded with `npm create aktion@latest` — and check:

- **Highlighting** — comments, strings, `$state` atoms, and component calls are
  each distinct.
- **Diagnostics** — type `Card([], { junk: 1 })` for an unknown-prop error, and
  `Cardd([])` for the unknown-component warning with a "did you mean" hint.
- **Quick docs** — <kbd>Ctrl/Cmd</kbd>+<kbd>Q</kbd> on `Card`.
- **Completion** — <kbd>Ctrl/Cmd</kbd>+<kbd>Space</kbd>; then `$util.` for member
  completion.
- **Go to Declaration** — <kbd>Ctrl/Cmd</kbd>+<kbd>B</kbd> on an imported binding
  should open the other file at its declaration.
- **Language Servers tool window** — the server should be *Started*; its log
  shows the trace when you enable it in settings.

**Iterating on the language server** rather than the plugin is much faster than
restarting the sandbox: point Settings → Languages & Frameworks → Aktion at your
checkout's `editors/lsp/dist/server.mjs`, run `npm run watch` in `editors/lsp`,
and then just restart the server from the Language Servers tool window after each
rebuild.

## Publishing to JetBrains Marketplace

### One-time setup

1. **Create a JetBrains account** and sign in at
   <https://plugins.jetbrains.com>.
2. **Generate a permanent token**: your profile → **My Tokens** → create a token
   with the *Marketplace* scope. This is `PUBLISH_TOKEN`.
3. **Set up plugin signing.** Marketplace requires signed plugins. Generate a
   certificate and private key once:

   ```bash
   openssl genpkey -aes-256-cbc -algorithm RSA -out private.pem -pkeyopt rsa_keygen_bits:4096
   openssl req -key private.pem -new -x509 -days 3650 -out chain.crt
   ```

   Keep both out of the repo (`.gitignore` already covers `*.pem`). See the
   [signing docs](https://plugins.jetbrains.com/docs/intellij/plugin-signing.html).
4. **First upload must be manual.** A plugin that has never been published cannot
   be created by the API. Build it, then upload
   `build/distributions/aktion-jetbrains-<version>.zip` at
   <https://plugins.jetbrains.com/plugin/add>. Pick a licence (MIT) and wait for
   JetBrains to review it — first-time review typically takes a couple of
   business days. Subsequent updates are automatic.

### Releasing an update

```bash
cd editors/jetbrains

# 1. Bump the version (keep it in lockstep with the runtime's package.json).
#    Edit `pluginVersion` in gradle.properties.

# 2. Verify before you ship.
./gradlew verifyPlugin

# 3. Publish.
export CERTIFICATE_CHAIN="$(cat chain.crt)"
export PRIVATE_KEY="$(cat private.pem)"
export PRIVATE_KEY_PASSWORD='…'
export PUBLISH_TOKEN='…'
./gradlew publishPlugin
```

`publishPlugin` signs and uploads in one step. A plain SemVer version publishes
to the `default` channel; a pre-release label routes automatically to a matching
channel — `0.6.0-beta.1` goes to `beta` — via the `channels` mapping in
`build.gradle.kts`. Users opt into those channels by adding the corresponding
custom repository URL.

### CI publishing

Store `PUBLISH_TOKEN`, `CERTIFICATE_CHAIN`, `PRIVATE_KEY`, and
`PRIVATE_KEY_PASSWORD` as repository secrets and run, on a tagged release:

```bash
npm ci && npm run build
cd editors/jetbrains
./gradlew verifyPlugin publishPlugin
```

> The Marketplace listing text is the `<!-- Plugin description -->` block of
> [`../README.md`](../README.md) — `build.gradle.kts` extracts it and fails the
> build if the markers are missing. Edit the README, not `plugin.xml`.

## Bumping the platform

`platformType` / `platformVersion` in `gradle.properties` pin the IDE the plugin
compiles against; `pluginSinceBuild` pins the oldest IDE it loads in.

- Compiling against **IntelliJ IDEA Community** (`IC`) is intentional: it is the
  lowest common denominator, so a build that links there loads in every IDE. Only
  raise it if the plugin starts needing an API that Community lacks — and if that
  ever happens, prefer finding another way, because it would drop Community users.
- `pluginSinceBuild = 242` is set by **LSP4IJ's** own minimum (2024.2). Raising it
  strands users; lowering it will not work.
- `untilBuild` is deliberately left open in `build.gradle.kts`. Run
  `./gradlew verifyPlugin` after a platform bump instead of pinning a ceiling.

Also bump `com.redhat.devtools.lsp4ij:<version>` in `platformPlugins` from time
to time, and re-run `verifyPlugin`.

## Keeping in sync with the runtime

When the runtime's language surface changes, this plugin usually needs **nothing**:

| Change in the runtime | What this plugin needs |
| --- | --- |
| Add / remove / rename a component | Nothing. Rebuild — completion, hover, diagnostics, and snippets all derive from the library. |
| Add a `$`-builtin (in `src/language/builtins.ts`) | Nothing. `syncAssets` regenerates the grammar's builtin overlay. |
| Add a new language-service capability (e.g. code actions, folding, inlay hints) | Expose it in `editors/lsp/src/server.ts` — the plugin picks it up from the server's advertised capabilities with no Kotlin change. |
| Change the semantic-token legend (`semanticTokenTypes` / `semanticTokenModifiers`) | Add the new type to `AktionSemanticTokensColorsProvider`. Unmapped types fall through to TextMate rather than being mis-coloured, so this is a soft failure. |
| Release a new runtime version | Bump `pluginVersion` in `gradle.properties`. |
